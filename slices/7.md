# Slice 7: Lighthouse CI — automated perf/a11y/SEO/best-practices baseline on every PR

Add Lighthouse CI as a second job in the existing GitHub Actions workflow. The job builds the site, boots `next start` on localhost, runs `@lhci/cli autorun` against `http://localhost:3000/`, and uploads results as a temporary public report. On the first run, budgets are **informational** (no threshold gating) so we capture a baseline without flaking the pipeline; future slices can ratchet thresholds upward once the baseline is known. No Vercel preview dependency — the workflow is self-contained.

## Behavior
- A pull request targeting `main` runs a second CI job named `lighthouse` in addition to the existing `verify` job, and the `verify` job remains independently green.
- The `lighthouse` job builds the site, starts `next start` on port 3000, waits for the server to respond, runs Lighthouse against `/`, and reports four category scores (performance, accessibility, best-practices, seo) in the workflow logs.
- The `lighthouse` job's conclusion is `success` whenever Lighthouse completes, regardless of category scores (assertions are informational on first run).
- The Lighthouse run is deterministic against a single URL (`/`) and uses a single run count to keep the job under ~3 minutes.
- A future regression that crashes `next start` or makes `/` unreachable causes the `lighthouse` job to fail (server-startup failure mode is real, score regressions are not).

## Approach
Approach: extend `.github/workflows/ci.yml` with a second job `lighthouse` that runs in parallel with `verify`. Steps: checkout, setup-node 20 with npm cache, `npm ci`, `npm run build`, start `next start` in the background with `&`, poll `curl -sf http://localhost:3000/` until ready (or timeout 60s), then `npx lhci autorun`. Configuration lives in `lighthouserc.json` at repo root: `ci.collect.url = ["http://localhost:3000/"]`, `ci.collect.numberOfRuns = 1`, `ci.collect.startServerCommand` omitted (we manage the server in the workflow step for clarity), `ci.assert.assertions = {}` (no gating thresholds on first run), `ci.upload.target = "temporary-public-storage"`. The local `lhci` script in `package.json` lets developers reproduce the run.
Gives up: gating thresholds (deferred until baseline is observed — first-run gating is the #1 source of Lighthouse CI flake), multi-URL coverage (single-page site, only `/` matters), Vercel preview integration (adds a webhook + token surface that isn't needed for a static personal site), historical trend storage via LHCI server (overkill — temporary public storage is fine for a portfolio).
